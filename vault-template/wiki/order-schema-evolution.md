# Synthesis: How Order Has Grown

This page exists because "why does `Order` look the way it does" spans two epics and one ADR — no single source answers it, which is exactly what a synthesis page is for (`CLAUDE.md` §6). It does not restate the schema; read `sources/contracts/openapi.yaml` for that, per the orientation-vs-compliance rule (`CLAUDE.md` §2).

- **EPIC-101** ([[EPIC-101-checkout-redesign/srs]]) defined `Order` as part of shipping `createCheckout`/`listOrders`/`getOrder`/`cancelOrder`, cut as capability slices rather than a backend/frontend/QA split ([[adr-0002-capability-slices]]).
- **EPIC-102** ([[EPIC-102-bulk-order-management/srs]]) needed `Order` to carry a cancellation timestamp, for `bulkCancelOrders` and (retrofitted) `cancelOrder` alike. Because `contracts/` is flat and global, this showed up as a collision against EPIC-101's already-shipped schema, not a second file quietly disagreeing with the first.
- **[[adr-0004-epic-102-order-seam]]** is why the collision resolved the way it did: an additive, nullable field, landed as its own serial seam ticket before EPIC-102's main slice started, specifically so EPIC-101's four operations and STD scenarios needed zero changes.

If a third epic changes `Order` again, that change belongs here too, cited the same way — this page is regenerated by ingest as sources accumulate (`CLAUDE.md` §9), not maintained by hand.
